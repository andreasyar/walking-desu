новые разновидности предметов или отдельное окно экипировки не вводились.

## Владение состоянием и контракт

`PlayerManager` — общий монитор мира. `ItemController` владеет наземными
предметами и наборами их видимости, `Player.inventory()` — единственным
инвентарём игрока. Порядок блокировок: мир → Inventory. ID выдаёт существующий
`IdManager`, отдельного счётчика предметов нет.

Подбор проверяет условия до изменения состояния. Под одним монитором
проверяется вместимость, пополняется канонический стек, удаляется наземный
предмет, очищается видимость и ставятся сообщения в очереди. Сетевая запись
остаётся в sender-потоке соединения. Конкурентный запрос видит уже изъятый
предмет и отклоняется. Закрытие соединения сериализуется с обработкой команд:
завершённый подбор возвращается в мир через выпадение; иначе предмет остаётся
лежать. Исключение переполнения не меняет ни мир, ни инвентарь.

| Сообщение | Данные и получатели |
| --- | --- |
| `PickupItemMessage` / PICKUPETCITEM | Клиент → сервер: только ID наземного предмета. ID игрока не принимается от клиента. |
| `AppearItemMessage` / APPEARETCITEM | Сервер → находящиеся в радиусе наблюдатели: GroundItem со стеком (ID, тип, количество) и координатами. |
| `DisappearItemMessage` / DISAPPEARETCITEM | Сервер → видевшие предмет: ID. Инвентарь не меняется. |
| `InventoryAddMessage` / INVENTORYADDETCITEM | Только владельцу: положительная дельта количества, тип и ID канонического стека. После A/7 и B/5 приходят дельты A/7 и A/5. |
| `InventoryRemoveMessage` / INVENTORYREMOVEETCITEM | Только владельцу: ID стека и количество списания. При смерти приходит до Respawn. |
| `PickedUpMessage` / PICKEDUP | Только подобравшему: ID наземного предмета, отдельное подтверждение; повторно инвентарь не меняет. |

При успешном подборе порядок очереди владельца: Disappear → InventoryAdd →
PickedUp. При смерти игрока после Death приходят InventoryRemove, появление
выпавшего золота в текущей видимости и затем Respawn. При отключении игрок
удаляется из списка наблюдателей, его золото появляется у оставшихся.
Новая сессия создаёт пустой инвентарь и получает актуальные наземные предметы.

Смерть и выпадение выполняются в терминальном пути CombatController после
изъятия попавшего снаряда; отмена остальных попаданий не позволяет повторить
смерть/награду. Башни не оставляют золота. Пропуски и очистка NPC не вызывают
выпадение; полный сброс сохраняет уже созданные предметы.

Клиентский ItemManager изменяется на EDT, как и PlayerManager. Появление
заменяет запись того же ID, повторное исчезновение безопасно. Список
инвентаря не совмещён с наземными предметами. Смена ID уже существующего стека
считается рассогласованием и закрывает текущее соединение без завершения JVM.
При разрыве очищаются предметы, инвентарь и ожидание подбора. Ожидание также
отменяется при исчезновении предмета, своей смерти, ПКМ/Esc, новом клике или
строительстве; при остановке перед препятствием можно подойти и повторить клик.

Протокол расширен; обновлять клиент и сервер нужно одним комплектом.
Новые сообщения используют serialVersionUID=12L, формат несовместим с 3.x
и предыдущими промежуточными сборками wand6.

## Окружение и воспроизведение

Сборка: контейнер `walking-desu_devcontainer-dev-1`, Temurin JDK 21.0.13+9,
Gradle Wrapper 9.8.2. GUI: Linux, хостовая OpenJDK 25.0.4.1, DISPLAY=:0,
WAYLAND_DISPLAY=wayland-0. Ресурсы `.devcontainer/assets/wand6`; монеты взяты
из локального внешнего набора 3.2. Снимки — содержимое живых Swing-окон
через printAll на EDT, не снимки рабочего стола.

```sh
docker exec walking-desu_devcontainer-dev-1 ./gradlew check :client:visualCheck \
  :client:itemGuiCheckAgent :server:distTar
python3 tools/check-wand6-items.py --assets .devcontainer/assets/wand6
# Уточнённые предметные проверки и финальная упаковка:
docker exec walking-desu_devcontainer-dev-1 ./gradlew :server:itemCheck \
  :client:visualCheck :client:verifyClientPackaging :server:distZip
docker exec walking-desu_devcontainer-dev-1 jdeps --print-module-deps \
  server/build/libs/wand6-server-4.2.0-dev-standalone.jar
```

Все команды PASS, exit 0; `jdeps` — `java.base`. Полный check включал
инвентарь, движение, карту, network smoke, multiplayer, combat, tower defence.
Уточнённый предметный прогон после добавления случаев 50/51 и мёртвого игрока:
порт **37679**. Прогоны регрессий: PvP **40477**, multiplayer **44547**,
production smoke **36349**, tower defence network **44367**; его
детерминированная часть проверила сохранение предмета при полном сбросе.

Первый повторный запуск ItemCheck обнаружил гонку в проверочном Peer.since:
CopyOnWriteArrayList.subList мог инвалидироваться между созданием и копированием.
Теперь сначала берётся целый неизменяемый снимок, затем его срез. Это исправление
проверочного помощника; признаков соответствующего дефекта в игровом коде нет.
После исправления полный check и уточнённый ItemCheck прошли.

Отдельно проверены содержимое клиентских и серверных ZIP/TAR и вложенных JAR:
нет изображений, Check-классов и GraphicalAgent. Фикстура предметов и замороженное
начало движения NPC живут только в checks source set; серверный production-протокол
не содержит команд выдачи золота, создания NPC или ускорения волн.

## Границы результата

Общая релизная матрица 3.2 на 4.x, RC, проверка отката и длительный ресурсный
прогон остаются этапу 13. В этом этапе нет проверки Windows/macOS, новой БД
или сохранения инвентаря после перезапуска сервера. Прямой путь к монетам
может упереться в непроходимую клетку; автопоиск обхода не вводился. Исторические
графические ресурсы и все PNG остались локально; публичные архивы без изображений.
