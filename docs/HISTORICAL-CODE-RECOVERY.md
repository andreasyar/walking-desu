# Оценка восстановления последнего исторического кода

Дата исследования: 1 ноября 2026 года.
База работающей линии: `240235e`; последний исторический код: `b9d8a80`
(3 января 2011 года). Текущая ветка: `codex/gradle-game-3.1`.

## Вывод

Восстановить запуск последней линии реально. Вернуть в неё полноту старой
игры — отдельная работа по завершению миграции, а не исправление сборки.
После базы всего 12 коммитов, но они содержат две последовательные переделки.
Накопленный diff `src/`: 112 файлов, 5918 добавленных и 4276 удалённых строк
с распознаванием переименований Git. Это размер изменения, не оценка труда.
Сама последняя линия `wand6` — 40 Java-файлов, 3141 строка, включая комментарии.

Более поздние `0e15b5c` и `7ab4355` также компилируются. Поэтому `240235e`
нельзя называть последним компилируемым коммитом. Компиляция `7ab4355`, однако,
не означает работоспособность: перенос отрисовки уже содержит явные разрывы.

## Что проверено

Все 13 состояний, включая базу, извлечены через `git archive` в `/tmp`.
Каждое компилировалось независимо, без классов других версий:

```sh
find "$snapshot/src" -name '*.java' > "$snapshot/sources.txt"
javac --release 21 -encoding UTF-8 -Xmaxerrs 10000 \
  -d "$snapshot/classes" @"$snapshot/sources.txt"
```

Использован Temurin JDK 21.0.13 в существующем dev-контейнере. Проверялись
Java-исходники, а не исторические Ant/NetBeans-скрипты. Ресурсы для компиляции
не требовались. Количество ошибок — число диагностик `error:` одного вызова
компилятора; это не количество независимых дефектов. Каталоги результатов

## Переделка существующей игры: до 6425041

Замысел разумный: отделить визуализацию от модели, унифицировать предметы,
вынести серверные задачи из монолитного JavaTestServer. Но миграция переходила
к следующему слою раньше, чем предыдущий становился согласованным.

Конкретные примеры в `7ab4355`, установленные чтением кода:

- `client/GameField.java`: добавление снарядов, попаданий и предметов в старую
  очередь отрисовки закомментировано; UnitPainter принимает только Unit.
- `client/UnitAnimator.java`: создаются собственные экземпляры анимаций,
  после чего вызывается getSprite, но запуск и обновление этих экземпляров
  через run не подключены. WUnit запускает другие экземпляры. В частности,
  MovementAnimation требует заполненного beg, а UseSkillAnimation изначально
  остановлена. Есть прямые предпосылки исключений при отрисовке.
- UnitAnimator создаёт DeathAnimation для каждого типа юнита, а её конструктор
  допускает только peasant и poring и вызывает System.exit для остальных.
  Это конфликтует с башнями и peon.
- `GameField.addDrawable/removeDrawable` стали package-private, тогда как
  SelfExecutor продолжает искать методы через Class.getMethod, который ищет
  только public-методы. Асинхронные обёртки этих методов несовместимы с ним.

Эти пути не проверялись графическим запуском; перечислены конкретные
несогласованности, а не утверждение о том, что каждая возникает сразу при входе.

В `0962dd6` и `6425041` одновременно живут common и newcommon; клиент,
сообщения и сервер не переведены согласованно. Позднее в старом дереве
остаются ссылки на уже отсутствующие классы и на непубличный
wand6.client.ServerInteraction. Значительная часть 104 ошибок последнего
снимка относится к этому оставшемуся старому коду, а не к новой линии.

## Последняя линия wand6: что действительно работает

Проведён отдельный эксперимент: все 40 файлов `b9d8a80/src/wand6` успешно
скомпилированы с `240235e/classes` в classpath. Исходники wand6 не правились.
Это намеренно смешанный диагностический вариант, не чистая сборка b9d8a80.
Для компиляции нужны старые GameField, LoginDialog и WanderingMap;
прямые импорты находятся в GUI и WandJPanel. Часть связей — остаточные поля
и параметры. Их устранение ограниченно по объёму.

Новый сервер затем запущен из этих wand6-классов на случайном локальном
порту внутри dev-контейнера. В тесте использованы два клиента на реальных
Socket/ObjectInputStream/ObjectOutputStream. Старые классы при этой
серверной проверке в runtime-classpath не включались.

Подтверждено исполнением:

- HELLO + NAME → WELCOME для двух разных игроков с ID 1 и 2.
- Запрос фрагмента (0,0) → MAPFRAGMENT, карта высот 32×32.
- Запрос движения (300,400) → MOVE с указанными координатами своему клиенту.
- Второй клиент не получил уведомления за 1500 мс. Чтение VisibleManager
  подтверждает причину: коллекции видимости нигде не заполняются.
- Запрос движения (-100,-200) также принимается сервером.
- Отдельный вызов CurveMovement.start(300,400,123) немедленно возвращает
  текущие координаты (300,400): это телепортация-заглушка, а не движение.

Отдельно CMapFragment отрисован в BufferedImage без графического экрана.
Проверочный фрагмент включал сушу и воду. Получено изображение 1024×1024
без исключений при использовании локального кандидата атласа summer.png.
Это подтверждает работоспособность пути отрисовки одного фрагмента;
целостность GUI и правильность всех стыков/вариантов тайлов не проверены.

## Что отсутствует или не завершено в wand6

| Подсистема | Состояние последнего кода | Что потребуется |
| --- | --- | --- |
| Сборка и запуск | Старая и новая линии смешаны; wand6 отдельно компилируется с адаптацией classpath | Выделить модули, убрать старые UI-зависимости, задать точки входа. |
| Карта | Генерация, запросы и тайловая отрисовка реализованы | Подключить атлас, проверить соседние фрагменты, границы, повторную загрузку. |
| Движение | Запрос/ответ работают; CurveMovement — Dummy | Реализовать скорость, интерполяцию, время начала, ограничения координат. |
| Персонаж | drawPlayers рисует одну красную точку в центре | Вернуть спрайты, направления, анимации и привязку к координатам мира. |
| Другие игроки | Есть список игроков, но нет завершённого обмена появлением/исчезновением и видимостью | Вход/выход из области видимости, создание/удаление на клиенте, рассылка движения. |
| Бой/PvP | Старые обработчики закомментированы; завершённого нового пути нет | Перенести здоровье, атаки, снаряды, попадания, смерть и возрождение. |
| Башни и монстры | Старые реализации остались вне нового игрового контура | Перенести появление, волны, выбор целей и боевые задачи. |
| Предметы и инвентарь | Старые обработчики закомментированы; имена enum сами по себе функций не дают | Перенести модель предметов, подбор, выпадение и синхронизацию инвентаря. |
| Текст | Текст уходит серверу и сохраняется в модели | Реализовать показ и передачу другим игрокам. |
| Сеть и потоки | Есть очереди и обработчики, но жизненный цикл не завершён | Проверить отключение, освобождение игрока/сокетов, остановку потоков и обработку ошибок без завершения всего процесса. |

В частности, серверный PlayerManager не удаляет отключившихся игроков,
а шаблон проверки пустоты очереди и последующего wait допускает потерянное
уведомление. Это выводы по коду, не воспроизведённые нагрузочным тестом.

## Ресурсы

Последний CMapFragment загружает `img/summer.png`. В текущем наборе
`.devcontainer/assets/client` этого файла нет; требование отсутствует и в
текущем `client/required-assets.txt`. Исторический профиль v22 также отмечает
его как missing-exact-path и предлагает кандидатов, а не доказанное совпадение.

В локальном архиве имеется
`recovered/orphan-branch-sprite-review/images/local-img/tiles/summer.png`,
512×768. Его размеры допускают все используемые вырезки, и именно с ним
прошёл описанный выше тест отрисовки. Он пригоден как технический кандидат;
точное соответствие историческому атласу не установлено. Ресурсы в Git
в ходе исследования не добавлялись.

## Рекомендуемый путь

Если цель — получить именно последнюю архитектуру, разумно восстанавливать
wand6 на основе b9d8a80 отдельными этапами, сохраняя доступную линию 3.1.
Нужно переносить завершённые обязанности подсистем, а не последовательно
применять каждый промежуточный сломанный коммит.

1. **Собираемый последний прототип.** Выделить wand6 в текущую Gradle-сборку,
   устранить три старые клиентские зависимости, подключить проверяемый набор
   ресурсов и подтвердить вход/карту в настоящем окне. Объём ограниченный.
2. **Основа многопользовательской игры.** Реальное движение, персонажи,
   видимость двух игроков, появление/исчезновение, отключение и границы карты.
   Это уже завершение архитектурных механизмов, объём средний.
3. **Возврат возможностей 3.1.** Переносить отдельно PvP, башни/монстров,
   предметы/инвентарь. Каждый шаг завершать проверкой соответствующего
   игрового сценария между клиентом и сервером. Совокупный объём существенный.

Для первого этапа работа выглядит оправданной: компиляция новой линии,
протокол и отдельная отрисовка уже подтверждены. Для всей игры нельзя честно
обещать короткий ремонт: готового нового PvP или инвентаря, которые осталось
лишь включить, здесь нет. Точность календарной оценки до первого этапа низкая;
назначать срок всей миграции по количеству ошибок компилятора было бы неверно.

Если цель — улучшить существующую работающую игру с минимальными затратами,
дешевле выборочно перенести полезные идеи в 3.1: разделение визуализации,
серверные контроллеры, типизированные сообщения и доработки карты. При таком
варианте нужно устранить описанные разрывы, а не брать UnitAnimator целиком.

Графический запуск клиента, игровой бой, башни и инвентарь последней линии
в этом исследовании не объявляются проверенными. Новая сеть несовместима
со старым сервером: при миграции клиент и сервер нужно менять согласованно.
