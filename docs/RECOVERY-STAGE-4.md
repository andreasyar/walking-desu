## Контракт сообщений и состояние

- `APPEARETCITEM`: ID наземного предмета, координаты, тип, количество.
- `DISAPPEARETCITEM`: только ID наземного предмета. Не меняет инвентарь и не
  означает успешный подбор. Повторное исчезновение безопасно.
- `PICKUPETCITEM`: запрос клиента; сервер игнорирует переданный pickerId и
  берёт игрока из соединения. При успехе подтверждение получает только владелец.
- `INVENTORYADDETCITEM`: положительная прибавка количества и ID канонического
  стека инвентаря. Например, при подборе предметов ID=A (7) и ID=B (5)
  владелец получает прибавки A/7 и A/5; итог — один стек A/12.
- `INVENTORYREMOVEETCITEM`: списание по ID/количеству, включая полный стек.
  Создание временного объекта для удаления и сравнение по ссылке не используются.

Общий монитор — экземпляр `VisibleManager` (`vm`); порядок блокировок всегда
`vm` → `Inventory`. Под ним выполняются обновление видимости, проверка
соединения/существования/расстояния (не более 50 мировых единиц), проверка
вместимости, изъятие из мира, зачисление, очистка видимости и постановка
сообщений в очереди. Выпадение при смерти, добавление монет монстров и
отключение используют тот же монитор. Сетевая запись выполняется sender-потоком.
Этап 5 должен использовать этот путь, без второго владельца предметных коллекций.

При разрыве соединения золото игрока возвращается в мир в его текущей позиции
с прежним ID стека. Поэтому запрос, гоняющийся с отключением, либо не выполняется,
либо его результат возвращается как выпавший предмет. Это также применяется
при обычном выходе: постоянного сохранения инвентаря в этой игре нет.

Для предметов нужен уникальный ID и при одновременной работе сетевых потоков
и задач мира; существующий общий счётчик ID заменён на `AtomicLong` уже здесь.
Общий рефакторинг боевых контроллеров и жизненного цикла задач остаётся этапу 5.

На клиенте исчезновение разрешает ID внутри очереди GameField, после более
раннего появления. Это устраняет гонку, когда пакет исчезновения получен раньше,
чем очередь успела добавить предмет. Удаляются модель, Drawable и выделение;
повторное появление заменяет старый Drawable того же ID. Инвентарь изменяется
только собственными сообщениями. Ошибка применения инвентаря закрывает текущее
соединение; reader/writer больше не завершают JVM через `System.exit`.

## Окружение и команды

Сборка: контейнер `walking-desu_devcontainer-dev-1`, Temurin JDK 21.0.13+9-LTS,
Gradle Wrapper 9.8.2, ресурсы `.devcontainer/assets/client`.
Графический прогон: хост Linux, OpenJDK 25.0.4.1, DISPLAY=:0/XWayland.

В контейнере, из `/workspace`:

```sh
./gradlew build :client:publishDev
```

PASS. `build` включает `:common:inventoryCheck`, `:client:regressionCheck`,
`:server:itemNetworkCheck`, `:server:networkSmoke` и сборку дистрибутивов.
Сохранено прежнее предупреждение unchecked cast сетевого пакета клиента.

На хосте, из корня репозитория, после сборки:

```sh
java -cp 'client/build/classes/java/checks:.devcontainer/artifacts/client/lib/*' \
  client.GraphicalItemCheck \
  'server/build/classes/java/checks:server/build/libs/walking-desu-server-3.1.0-dev-standalone.jar'
```

PASS, код выхода 0; итоговый графический сервер использовал порт 41087,
прежний NetworkSmokeCheck — порт 39507. Драйвер запускает отдельную JVM сервера на порту 0,
два настоящих Swing-окна с GameField/ServerInteraction и отдельными сокетами.
Начальные монеты задаются проверочной фикстурой `ItemNetworkCheck fixture`;
в production-протоколе нет команд создания тестовых предметов.
Драйвер использует обычные сообщения движения, PickupTask и PvP.
Проверка авторитетного серверного количества и гонок отдельно выполняется
`ItemNetworkCheck` с настоящими сокетами и доступом к миру через reflection
только в checks source set. Фикстуры не входят в обычные JAR и дистрибутивы.

## Совместное обновление и ограничения

Протокол несовместим с предыдущей сборкой: изменились Serializable-классы,
имена enum и смысл уведомления о подборе. Остановить старые клиент и сервер,
собрать комплект из одного коммита, обновить серверный JAR и клиент вместе,
затем запустить сервер и переподключить клиентов. При откате также возвращать
оба компонента. Серверный JAR из `server/build/libs` соответствует сборке;
старый `.devcontainer/artifacts/server/server.jar` автоматически не заменялся.
Работающий dev-сервер на 45000 не перезапускался.

Длительная ручная игра, полный цикл волн и общий рефакторинг серверных гонок
здесь не выполнялись. При принудительной остановке проверочного сервера reader ещё может напечатать
EOFException; тест уже завершён, оба сценария GUI закончились с кодом 0.
Согласованность предметов проверена перечисленными
сценариями; сохранение после перезапуска процесса не добавлялось.
Следующий этап — 5: R07–R10 и серверная часть R13.
