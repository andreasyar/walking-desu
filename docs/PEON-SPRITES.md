# Восстановление атаки и смерти peon

1 ноября 2026 года пользователь предоставил два локальных исходных листа:
`.devcontainer/assets/client/img/peasant.png` и `peon.png`.
Оба имеют размер 360×936: пять столбцов и 13 строк, ячейки 72×72.
Исходники, нарезанные PNG, резервные копии и превью остаются вне Git.

## Разметка и прозрачность

Координаты строк и столбцов ниже начинаются с нуля.

| Строки | Состояние | Результат этой операции |
| --- | --- | --- |
| 0 | Покой | Существующие peon_stand сохранены |
| 1–4 | Ходьба | Существующие peon_walk сохранены |
| 5–9 | Атака | 40 файлов peon_attack, пять кадров для восьми направлений |
| 10–12 | Смерть | 12 файлов peon_death: ne/nw/se/sw, три кадра |

Столбцы атаки: N, NE, E, SE, S. NW/W/SW получаются отражением NE/E/SE.
У смерти первые три столбца одинаковы, как и два последних. Модель загрузки
сохраняет прежнее распределение направлений: N/NE/E используют ne, NW/W — nw,
S/SW — sw, SE — se. Это существующие ограничения исходного листа.

Координаты независимо сопоставлены с готовыми кадрами peasant: совпало 51
из 52 изображений после нормализации невидимого RGB. Единственное исключение —
`peasant_attack/sw_05.png`: в исторической нарезке этот кадр не отражён.
Программа проверяет именно это исключение, а новый peon SW получает правильное
отражение. Кадры peasant не изменены.

Фон peon имеет точный цвет `(252, 252, 252)`. Программа делает прозрачными
все 303209 пикселей этого цвета, включая 382 пикселя в замкнутых промежутках,
не достижимых обычной заливкой от границы листа. Чёрная обводка и серые
светлые детали сохраняются. Масштабирование, сглаживание и удаление
приблизительно похожих цветов не применяются. Холст каждого кадра остаётся
72×72, поэтому положение основания соответствует исходной сетке.

SHA-256 исходников:

- `peasant.png`: `db8d1414bf1c533c5bbd40147c2d990c048b72a549b35b8b7ec4b6358b965140`
- `peon.png`: `ff0aadcbb77e3580150e47f8993b069fca85aa68e707b4326afec8796c2ecbf7`

## Повторная нарезка

Нужны Python 3 и Pillow. Из корня проекта:

```sh
# Создать превью и проверить сопоставление, не меняя рабочие спрайты:
python tools/cut_peon_sprites.py

# Установить кадры, предварительно сохранив старые:
python tools/cut_peon_sprites.py --install
```

Программа [tools/cut_peon_sprites.py](../tools/cut_peon_sprites.py) создаёт
`client/build/peon-sprites/`: две папки кадров, `preview.png`, `preview.gif`
и `manifest.json` с координатами ячеек, отражениями и контрольными суммами.
Параметры `--assets` и `--output` позволяют использовать другие локальные пути.
При установке резервная копия сохраняется в отдельной новой папке
`.devcontainer/assets/client/sprite-backups/peon-*`; исходные листы не меняются.
Первая установка сохранила старую атаку в `peon-aeaa6ifv/peon_attack/`.
Для возврата старой атаки можно скопировать содержимое этой папки обратно
в `img/peon_attack/`. Полный возврат прежней смерти требует также возврата
кода fallback, поскольку новый клиент явно загружает peon_death.

## Подключение и проверки

`UnitAnimations` теперь выбирает собственный `peon_death`, а `DeathAnimation`
и `DirectionalSpriteSet` поддерживают новый набор. Прежняя подмена смерти
на peasant удалена. Атака использует восстановленные PNG по прежним путям.
В обязательном манифесте теперь 292 пути вместо 280. Исходные листы
`img/peasant.png` и `img/peon.png` исключены из клиентского JAR.

Проверено:

- Все 52 установленных кадра имеют размер 72×72, непустую альфу, совпадают
  с контрольными суммами результата и отличаются от одноимённых peasant.
- Удалённый фон не остался непрозрачным ни в одном выходном кадре.
- Превью всех кадров просмотрено на шахматном фоне.
- `./gradlew build :client:publishDev` прошёл в dev-контейнере с JDK 21;
  регрессионная проверка использует собственную смерть peon для всех направлений.
  Сетевая smoke-проверка прошла на изолированном порту 41645.
- В JAR присутствуют 12 кадров peon_death и отсутствуют оба исходных листа.

Локальный клиент в `.devcontainer/artifacts/client/` обновлён. Сервер и
протокол не менялись; сервер на 45000 не перезапускался. Изображения доступны
только на машинах, куда отдельно перенесён локальный набор ресурсов.
