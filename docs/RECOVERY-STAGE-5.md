## Владение, блокировки и жизненный цикл

`WorldState` создаётся один раз на экземпляр сервера. Порядок блокировок —
**WorldState → Inventory**. Он заменил `vm → Inventory` согласованно во всех
активных путях: видимость, движение, вход/выход, подбор, выпадение, смерть,
создание объектов и периодические контроллеры. Контроллеры получают тот же
экземпляр явно. Очереди коллекций позволяют безопасную диагностику, но
согласованность составных операций обеспечивает монитор мира.

Предметные операции этапа 4 сохранены: проверка соединения, существования,
дистанции и вместимости, изъятие, зачисление, очистка видимости и постановка
сообщений составляют одну операцию. Inventory и общий AtomicLong не дублируются.
Сетевая запись выполняется вне монитора мира.

Снаряд хранит ID атакующего/цели и собственную траекторию, разрешает ID через
действующий реестр при tick. До назначения Future tick ничего не меняет.
Отмена выставляет терминальное состояние даже без Future; позднее назначение
сразу отменяет Future. При попадании задача становится терминальной **до**
урона. Смерть отменяет остальные снаряды этой жизни до восстановления здоровья;
старые попадания не атакуют возрождённого игрока. Выход участника, удаление
монстра на финише и сброс башен отменяют связанные задачи. Штатная остановка
сервера отменяет все снаряды, периодические задачи и закрывает соединения/порт.

Ровно один владелец завершает смерть. Золото волнового монстра выдаётся сразу
в этой операции, вместо отдельной повторной обработки контроллером волн.
Случайное количество 1–99 и привязка около места смерти сохранены. Монстры,
создаваемые запросом карты, как и в базе, не выдают волновую награду.
Действующий порядок пакетов игрока сохранён: **HIT → списание инвентаря
(если есть) → teleport → deathplayer**. Новая задержка смерти 3000 мс не вводилась.

## Ники и автоматический вход

`common.PlayerName` задаёт общий контракт клиента, сервера и проверок:
3–10 символов по прежнему правилу Java String.length; кавычки и переводы
строк запрещены как разделители текстового протокола. Проверены допустимые
границы 3/10 и отказ для 2/11 символов. Все тестовые ники соответствуют контракту.

Обычный запуск сохраняет диалог выбора ника. Только явный режим
`-Dwalkingdesu.testMode=true` вместе с `-Dwalkingdesu.testNick=stage5-one`
пропускает диалог/таймер и использует проверенное имя. Неправильное или
отсутствующее тестовое имя вызывает отказ до запуска потоков/соединения
в основном entry point. Один testNick без testMode не включает режим.

```sh
JAVA_OPTS='-Dwalkingdesu.testMode=true -Dwalkingdesu.testNick=stage5-one' \
  .devcontainer/artifacts/client/bin/walking-desu-client localhost 45001
```

## Окружение и команды

Сборка: существующий контейнер `walking-desu_devcontainer-dev-1`, Temurin
JDK 21.0.13+9-LTS, Gradle 9.8.2, локальные ресурсы `.devcontainer/assets/client`.
Из корня репозитория на хосте:

```sh
docker exec walking-desu_devcontainer-dev-1 ./gradlew build :client:publishDev
```

PASS. В build входят `:common:inventoryCheck`, `:client:regressionCheck`,
`:server:combatCheck`, `:server:itemNetworkCheck`, `:server:networkSmoke`.
Сохранено прежнее предупреждение unchecked cast клиентского сетевого пакета.
Исключение `injected hit failure` в combatCheck ожидаемо: тест проверяет
очистку аварийной задачи и успешное последующее попадание.

Графика: хост Linux, OpenJDK 25.0.4.1 с GUI, DISPLAY=:0/XWayland.
Обе команды из корня репозитория, код выхода 0:

```sh
java -cp 'client/build/classes/java/checks:.devcontainer/artifacts/client/lib/*' \
  client.GraphicalItemCheck \
  'server/build/classes/java/checks:server/build/libs/walking-desu-server-3.1.0-dev-standalone.jar'

java -cp 'client/build/classes/java/checks:.devcontainer/artifacts/client/lib/*' \
  client.GraphicalCombatCheck server/build/libs/walking-desu-server-3.1.0-dev-standalone.jar
```

Каждый драйвер запускает свой сервер на порту 0 и два настоящих Swing-клиента.
Предметный прогон использовал порт 36051, боевой — 35391. В боевом прогоне
используется production JAR и естественная первая волна, без тестовых команд
создания монстров. Соседний участок карты загружается сетевым запросом перед
программным движением, как при обычном клике клиента.

Изображения живых окон сохранены через printAll на EDT в
`client/build/item-graphical-check/` и `client/build/combat-graphical-check/`
и просмотрены: золото 12/15, башня, монстры, эффект и выпавшее золото видимы.
Это содержимое настоящих открытых окон, без захвата рабочего стола и диалога
разрешения Wayland. Логи сервера лежат в тех же каталогах. Артефакты build и
графические ресурсы в Git не добавляются.

## Ограничения и продолжение

Это автоматизированные игровые/графические прогоны, а не пользовательская
ручная сессия. Длительная нагрузка и выпуск RC относятся к этапу 6. Полный
сброс волн воспроизведён детерминированно на настоящих контроллерах; GUI
подтверждает естественную первую волну, но не ждёт в реальном времени всех
100 пропусков. При завершении графического драйвера старый клиентский reader
может напечатать EOFException после PASS, когда драйвер останавливает сервер.
Это не ошибка серверного сценария; штатный EOF сервера проверяется отдельно.

Работающий dev-сервер на 45000 не перезапускался, опубликованный
`.devcontainer/artifacts/server/server.jar` не заменялся. Новый серверный JAR
находится в `server/build/libs`. Перед ручной игрой следует запустить его
отдельно или остановить старый dev-сервер и опубликовать согласованный комплект.
