# Окружение разработки

Все файлы dev-окружения, его кэш и каталоги артефактов находятся в
`.devcontainer/`. Пути ниже указаны относительно корня репозитория.

Сборка выполняется в Dev Container, сервер работает в отдельном контейнере,
графический клиент запускается на хосте. Конфигурация IDE находится в
`.devcontainer/devcontainer.json` и использует сервис `dev` из `.devcontainer/compose.yaml`.
Контейнеры подключаются к общей сети Compose по умолчанию. Дополнительные
сервисы, например БД, будут добавляться по мере необходимости.

## Открытие проекта

На хосте нужны Docker с Compose v2 и IDE с поддержкой Dev Containers.
Открыть проект в IDE и выбрать **Reopen in Container / Open in Container**.
IDE сама соберёт образ, запустит сервис `dev` и откроет `/workspace` внутри
контейнера. Вручную запускать Compose или заполнять UID/GID не требуется.
Название команды и наличие всплывающего предложения зависят от IDE.

В контейнере установлены JDK 21, Git, SSH-клиент и инструменты просмотра
процессов. Перед запуском Compose IDE выполняет `init-host.sh` на хосте.
Скрипт получает `id -u` и `id -g` и автоматически записывает `LOCAL_UID` и
`LOCAL_GID` в `.devcontainer/.env`, сохраняя остальные настройки этого файла.
В dev-образе создаётся пользователь `dev` с этими ID; IDE, терминалы и сервер
запускаются с теми же UID/GID, что и пользователь хоста. Дополнительное
переназначение ID средствами IDE отключено (`updateRemoteUserUID: false`).
Запуск от root или с основной группой root отклоняется скриптом.
Файлы, создаваемые процессами контейнеров в bind mounts, принадлежат
пользователю хоста. Системные файлы внутри образов создаются при сборке от root.

Для ручного запуска Compose без IDE сначала выполнить на хосте
`sh .devcontainer/init-host.sh` из корня репозитория. Без подготовленных ID
Compose завершится с подсказкой. При смене пользователя хоста нужно заново
открыть Dev Container с пересборкой образа. Эта схема рассчитана на Linux
и обычный Docker Engine без переназначения UID через user namespaces.
Исходники доступны через bind mount; результаты сборки видны на хосте.
Для систем с SELinux используется общая метка bind mounts `z`.
При закрытии Dev Container IDE останавливает Compose-окружение.

Кэш Gradle хранится в `.devcontainer/cache/gradle` и переживает пересоздание контейнера.
Кэш, артефакты и локальный `.devcontainer/.env` исключены из Git.

## Сборка и артефакты

Сборка переведена на Gradle Wrapper 9.8.2 и JDK 21. Исходники разделены на
`common`, `client`, `server`; текущий выпуск — 3.2.0 на восстановленной базе 3.1.
Команды выполняются в терминале IDE внутри контейнера, из `/workspace`:

```sh
./gradlew build
./gradlew prepareDev
```

Wrapper загружает Gradle с проверкой SHA-256. Отдельная установка не нужна.
Первому запуску требуется сеть. Локальные изображения ожидаются в
`.devcontainer/assets/client/img/` либо в каталоге, переданном через
`-PclientAssetsDir=...`. Они не включены в Git. При отсутствии требуемых
файлов сборка клиента завершается с диагностикой.
Подготовка ресурсов, происхождение исходников и команды запуска описаны
в [README проекта](../README.md).

`prepareDev` публикует клиентский дистрибутив с библиотеками и скриптами
запуска в `.devcontainer/artifacts/client/`, а самостоятельный серверный JAR —
в `.devcontainer/artifacts/server/server.jar`. Отдельные задачи:
`:client:publishDev` и `:server:publishDev`.

Сервер читает JAR с UID/GID пользователя хоста и монтирует каталог только
для чтения. Публикация выполняется атомарным переименованием готового файла.
Перед публикацией новой версии работающий сервер нужно остановить, затем
снова запустить: загруженная JVM сама не перечитывает заменённый JAR.
Docker socket в dev-контейнер не передаётся. Автоматическое наблюдение за
исходниками и перезапуск пока не добавлены.

## Сервер и клиент

IDE автоматически запускает только `dev`.
Сервис `server` имеет профиль `runtime`. После настройки сборки и публикации
артефакта он запускается из терминала **на хосте**, из корня репозитория:

```sh
docker compose -p walking-desu_devcontainer -f .devcontainer/compose.yaml up -d --build server
docker compose -p walking-desu_devcontainer -f .devcontainer/compose.yaml logs -f server
```

Явное указание сервиса включает его независимо от профиля.
Имя Compose-проекта должно совпадать с именем из лога IDE; здесь приведено
имя `walking-desu_devcontainer`, использованное VS Code на текущей машине.
При отсутствии JAR сервер завершится с понятным сообщением.
После появления артефакта сервер можно будет добавить в `runServices`
конфигурации Dev Container для совместного запуска из IDE.
Docker socket в dev-контейнер не передаётся.

Сервер слушает `45000` внутри Docker-сети и доступен другим контейнерам как
`server:45000`. На хост порт опубликован только через `127.0.0.1:45000`.
Если нужен другой внешний порт, добавить `SERVER_HOST_PORT` в `.devcontainer/.env`
по примеру `.devcontainer/.env.example`. При следующем открытии проекта
скрипт сохранит эту настройку и обновит только UID/GID.

Клиент запускается на хосте с Java 21 с поддержкой графики и подключается к
`localhost:45000` либо выбранному внешнему порту. Графический доступ
контейнерам не нужен. Для запуска и отладки клиента на хосте можно открыть
второе локальное окно IDE с этим же проектом и установленным JDK 21.
Основное окно IDE, открытое в Dev Container, выполняет команды в контейнере.

При необходимости вручную остановить всё окружение с хоста, из корня репозитория:

```sh
docker compose -p walking-desu_devcontainer -f .devcontainer/compose.yaml --profile runtime down
```

Это dev-окружение с внешними артефактами. В релизный образ серверный
дистрибутив впоследствии будет включаться непосредственно.
